# Contract: Java Automation Parity Fixture Corpus v1

## Location and authority

The canonical corpus is the complete directory:

```text
fixtures/java-blue-automation-parity/v1/
├── manifest.json
├── SCHEMA.md
├── realtime.tsv
├── resolution.tsv
└── offline.tsv
```

All test consumers read these files or a build-directory byte-for-byte copy. No consumer may maintain a separate expected-value table or generated header as an independent authority.

## Common TSV rules

- UTF-8, LF line endings, one header row, no BOM.
- Fields are tab-separated; a field may not contain a literal tab or newline.
- Empty field means absence where the section schema permits it.
- Every record begins with stable `caseId`, `origin`, and `category`.
- `origin` is `curated` or `seeded`.
- Every binary64 input/output is exactly 16 lowercase hexadecimal digits containing raw IEEE 754 bits.
- Point lists use `timeBits:valueBits` entries separated by `;`.
- Expected failures use a stable diagnostic/exception category, not full exception text.
- Arbitrary output text is base64 of exact UTF-8 bytes.

## `manifest.json`

Required fields:

```text
schemaVersion = 1
generator.id
generator.version
java.release
javaBlue.repository
javaBlue.commit                 # exact 40-character SHA
javaBlue.sourceFiles[]          # relative path + SHA-256
referenceMethods[]
seed.algorithm = "SplitMix64"
seed.value                      # fixed hexadecimal seed
generationCommand              # uses $JAVA_BLUE_ROOT, never a local path
counts.total
counts.bySection
counts.byOrigin
counts.byCategory
```

The manifest MUST NOT contain a generation timestamp, absolute checkout path, JVM vendor build, hostname, or nondeterministic ordering.

## `realtime.tsv`

Required logical columns:

```text
caseId
origin
category
resolutionText
curve
pointsBits
evaluationTimeBits
expectedKind                    # bits | exception
expectedBits
expectedCategory
```

The authoritative linear expectations come from actual `Line.getValue(double)`. Extension-curve cases, if included, are labeled as quantizer-only expectations and do not claim a Java curve oracle.

The section MUST contain exactly 2,048 seeded finite linear cases generated by the documented, generator-owned SplitMix64 implementation, plus curated cases covering:

- empty/single/time-zero/direct point/endpoints;
- duplicate point times and last duplicate selection;
- before-first and after-last behavior;
- ascending, descending, flat, and zero crossing;
- exact grid and adjacent binary64 values;
- `+0.0`, `-0.0`, subnormal, near-overflow, and diagnostic non-finite cases;
- scale zero, negative scale, trailing zeros, exponent notation, scale greater than 18, positive underflow-to-zero, and coefficient values not recoverable from `double`.

A manager-level subset additionally records sample number and sample-rate bits so the production elapsed-time boundary is exercised.

## `resolution.tsv`

Required logical columns cover:

```text
caseId, origin, category, operation
parameterBdText, parameterLegacyText
lineBdText, lineLegacyText
expectedCoefficient, expectedScale, expectedCanonicalText
expectedDoubleBits, expectedActivation
expectedParameterSaveBase64, expectedLineSaveBase64
expectedKind, expectedCategory
```

Operations include exact parse/save, legacy normalization/save, and parameter/line load-ownership-save. Missing XML attributes are empty fields. Fixed IDs are used so generated UUIDs cannot make output nondeterministic.

## `offline.tsv`

Required logical columns:

```text
caseId, origin, category
resolutionText, pointsBits
renderStartBits, renderEndBits, instrumentId
expectedInitialBits
expectedInitializationBase64
expectedScoreBase64
expectedKind, expectedCategory
```

Expectations come from actual Java `CSDRender` paths, including `NumberUtilities.formatDouble`. Coverage includes positive/zero/negative resolution, ascending/descending/flat, render clipping, repeated times, zero-step behavior, final-note behavior, and render-end sentinel rules.

## Generator contract

The repository-owned generator calls actual artifacts built from the pinned Java Blue checkout. The wrapper:

1. accepts `--java-blue-root`;
2. verifies the exact commit and source SHA-256 values before execution;
3. verifies Java release 25 for schema v1;
4. builds/installs the required Java Blue Maven reactor artifacts;
5. executes the generator against those JARs;
6. writes stable sorted files with no machine-local metadata.

The generation and check interfaces are:

```bash
pnpm fixtures:java-automation -- --java-blue-root "$JAVA_BLUE_ROOT"
pnpm fixtures:java-automation:check -- --java-blue-root "$JAVA_BLUE_ROOT"
```

The check command regenerates in a temporary directory and performs a byte comparison against the committed directory.

## Consumer contract

Every consumer MUST:

- validate schema version and manifest section/category counts before testing cases;
- decode doubles from raw bits, never through decimal JSON/TSV numbers;
- compare output bits or output bytes exactly;
- print `caseId`, category, resolution, points, and time on failure;
- prove a deliberate one-bit expectation change fails;
- complete normal tests without Java, Maven, network, or an external checkout.

Vitest may use Node APIs in test-only fixture readers. CMake copies canonical TSV files into the build tree and passes their path to CTest; native production code gains no fixture parser or JSON dependency.
