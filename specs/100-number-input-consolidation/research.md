## Reference component contract (verified)

`components/workbench/panels/score-object/editors/jmask/CommitNumberInput.tsx`

- Props: `value: number`, `step = 0.1`, optional `min`/`max`, `className`, `onClick`, `onChange(v: number)`.
- Local string draft synced from `String(value)` while not focused; commits on **blur** and **Enter** (Enter also blurs); **Escape** reverts and blurs; **NaN reverts**; clamps to `[min,max]`; skips `onChange` when clamped value equals current value.
- Forwards `step/min/max` to native input; `className` composed via `cn()` (clsx + extended tailwind-merge, so caller utilities override the built-in `w-20 border-blue-border bg-blue-bg …` class — covered by `tests/caller-classname.test.tsx`).
- Also exports `CommitNumberField` (label + input row). Current consumers: `JMaskEditor.tsx:169` (seed), `jmask/TableEditor.tsx:311,320,327`, `jmask/generator-editors.tsx:44,70,96,101,192`, `jmask/modifier-editors.tsx:44,80`, `jmask/probability-editors.tsx:65,148,194,201,251,258,308,315,371,378`.
- Known defect motivating this feature: spinner/arrow changes update only the local draft; they reach the model only on blur/Enter, and Escape discards them.

## Clarification assessment (2026-09-04)

All native number input sites are feasible migration targets if the shared module supports commit-on-finish editing, live numeric updates, and caller-owned text drafts. The former KEEP verdicts described limitations of its current contract, not intrinsic barriers to reuse. This is source-based feasibility analysis; the extended interfaces and browser event behavior still require implementation validation.

- Stepping uses a valid typed draft, otherwise the last accepted value; only the stepped result is notified. Field bounds and validation still apply.
- Java reference checked: `~/work/nbprojects/blue/blue-ui-core/src/main/java/blue/soundObject/editor/jmask/ConstantEditor.java` uses live valid document updates and focus-loss recovery. Deferred typing is an intentional TypeScript policy, not universal Java parity.
- Dialogs retain draft ownership and OK-time validation/patching. Steps update that draft immediately; Cancel never persists it. Enter must consume the latest draft exactly once.
- Settings retain externally validated invalid drafts and current errors. OSC empty text maps to zero, which is invalid, not an automatic-port request.
- blue-x7 retains accepted-edit updates, undo granularity, mixed placeholders, and envelope/gesture ownership.
- Existing field parsing, rounding, clamp/revert/reject policies remain authoritative. Shared mechanics do not require moving domain validation, unit conversion, suffix markup, or persistence into the primitive.
- Number('') is zero, so the earlier claim that clearing Mixer/BlueLive directly writes NaN was incorrect. Empty-value and non-finite-value tests are separate obligations.
- Numeric text editors remain out of scope. Their exclusion is a scope decision, not proof that a reusable text-draft contract or adapter is impossible.

## (f) Resolved component gaps

The final interface is in [contracts/commit-number-input.md](contracts/commit-number-input.md). It resolves the audited gaps with three named exports over one private implementation, native attribute/ref forwarding, and pure field normalization rather than public mode/ownership flags.

- Invalid drafts and dialog transactions: `DraftNumberInput`; existing validator/error markup stays outside.
- Live updates and mixed values: `LiveNumberInput` with nullable display and explicit initial step base.
- Disabled/readOnly, accessibility, select/focus, style: native attribute/ref forwarding.

## Phase 0 decisions (2026-09-04)

### 1. Explicit step controls with native arithmetic

**Decision**: Keep native number input semantics and selectors; hide native spinner chrome, provide explicit up/down buttons, and handle ArrowUp/Down through the same operation. Use a detached native number input in the actual input's ownerDocument for stepUp/stepDown arithmetic.

**Rationale**: Spinner provenance has no portable InputEvent discriminator. Explicit controls allow the approved valid-draft/last-accepted-base rule and no-op behavior without guessing the source of a change event. Native arithmetic preserves directional grid alignment, step bases and decimals.

**Alternatives considered**: Native spinner event heuristics are not a reliable contract; replacing everything with text plus custom spinbutton ARIA violates input-structure requirements; a custom decimal stepping engine is unnecessary.

**Primary sources**: [Input Events](https://www.w3.org/TR/input-events-2/), [HTML stepping algorithm](https://html.spec.whatwg.org/multipage/input.html#dom-input-stepup), [WAI spinbutton pattern](https://www.w3.org/WAI/ARIA/apg/patterns/spinbutton/).

### 2. Any-step behavior

**Decision**: Preserve step="any" on the visible input, use increment 1 anchored at the chosen numeric value for explicit step controls. Keep step 0.1 as the existing component default; migrated native fields with omitted step explicitly use 1.

**Rationale**: Script stepUp/stepDown rejects any, while user stepping still needs a useful increment without rejecting arbitrary typed decimals. A read-only Playwright probe in installed Chrome 152.0.7977.76 confirmed ArrowUp changes 1.25 to 2.25 with any, and script stepUp throws InvalidStateError. This is observed Chrome evidence, not yet Electron 35 evidence; quickstart requires Electron verification.

**Alternatives considered**: Disabling all any steppers violates the consolidation goal; snapping any values to integers changes behavior; introducing a per-field increment option is unnecessary for the current inventory.

### 3. Three named interfaces and domain ownership

**Decision**: `CommitNumberInput`, `LiveNumberInput`, and `DraftNumberInput` share one private input/stepping implementation. Use pure resolvers for domain-dependent acceptance. Draft `onFinish` and `onCancel` callbacks opt into ownership of Enter and Escape respectively; absent callbacks leave those keys with the caller. Error rendering, storage conversion, undo and save/confirm operations stay at callers.

**Rationale**: Blue-x7 already patches valid integer edits live; TempoPoint owns strings until OK; Utility preserves invalid strings for main validation. Separate names make these contracts visible without exposing conditionally valid mode combinations. Row editors provide domain callbacks receiving current text, while dialogs omit them and retain transaction-level keyboard handling.

**Alternatives considered**: Keeping former exclusions fails the clarified scope; converting all fields to one behavior breaks existing workflows; a public mode plus independent keyboard-owner flag permits unsupported combinations; a generic form/validation framework increases complexity without need.

### 4. One finish path and synchronous accepted bookkeeping

**Decision**: A finish operation settles or cancels the current draft before calling blur or notifying the owner. Latest draft/accepted refs support rapid steps and callback arguments; caller snapshots remain authoritative.

**Rationale**: The previous component called finish both on draft Enter and its resulting blur, and draft Escape could run cancel followed by blur-finish. A settled marker removes duplicate/stale finishes. `DraftNumberInput` updates caller state on every edit and lets an existing dialog confirmation consume it; row callbacks receive text directly.

**Alternatives considered**: setTimeout/queued blur, global listeners, a new state-machine dependency, or persistence inside the component are unnecessary.

### 5. Migration domains and adapter scope

**Decision**: Preserve the 66-site native inventory, add a colocated SettingsNumberField export sharing SettingsField's label/description scaffold, and leave numeric text editors and CommitTextInput untouched. Keep native bounds separate from custom typed normalization.

**Rationale**: Native attributes are not evidence of JS clamping. Existing Tracker STEPS reverts out-of-range values, while some settings only expose attributes. Field step=1 alone does not establish integer-only values (for example BlueLive currently parses with Number). Migrations must preserve actual parsers and validators rather than infer new domains from the spinner step.

**Alternatives considered**: Rewriting domain rules or coercing string-typed project properties expands the feature and breaks compatibility; retaining duplicate generic lifecycle code defeats consolidation.

### 6. Verification and UI constraints

**Decision**: Use existing Vitest/jsdom and Playwright infrastructure with a focused shared component regression, browser event tests, source-boundary check and affected area suites. Keep styles in Tailwind with cn caller precedence and semantic roles. Preserve hosting-window conventions and existing input accessibility attributes.

**Rationale**: Pure/synthetic tests cannot validate native editing event order; source counting alone cannot distinguish wrapper call sites from actual inputs. The 66 count is static sites, not runtime controls. TypeScript is already installed for an AST-based boundary test; no new parser or browser dependency is needed.

**Alternatives considered**: A new test framework, test-only runtime inventory registry, blanket component rewrites, global listeners and CSS class cleanup are unnecessary.
