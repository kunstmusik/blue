# Contract: Generated-Mixer Benchmark Evidence

This is a developer-tool contract. It does not change the production Blue Engine protocol, project format, or runtime capabilities. The existing native automation benchmark and wrapper retain their current defaults, scenarios, fields and gates.

**Completion disposition (2026-10-25)**: The implementation is complete and
accepted. The owner accepts the recorded primary 32-sample shortfall; raw
numerical verdicts and the automated 10% threshold remain unchanged. macOS
correctness and all 72 representative comparisons pass. Native Windows/Linux
evidence remains deferred release validation under T038/T053/T056/T059 and is
not counted as a passed platform gate.

## Evidence levels

1. **Arithmetic microbenchmark**: helps prioritize opcode shapes; archived process-CPU measurements include startup/compile and do not discharge feature acceptance.
2. **Generated-mixer workload**: complete public-entry-point-generated CSD with original inexpensive deterministic sources, real mixer routing/control setup and resets. This is the primary performance gate; its per-block elapsed time includes all Csound work in that fixture and is not exact mixer-only CPU.
3. **Representative project**: includes instruments/effects/host behavior and reports its own before/after processing measurements. Do not extrapolate level 1 or 2 percentages to total app CPU or physical audio latency.

## Baseline capture and reproducibility

Baseline Blue revision: `6d884110241e55b779210eb93dee5071c0068c02`. Capture baseline fixture CSD plus public binding manifest before implementation, with original fixture input hash and generation profile. Candidate capture uses the same fixture identity/input and settings. If a baseline must later be reproduced in a worktree, use `.worktrees/<name>` within the repository; capture an identified clean revision, not an unrelated uncommitted checkout.

The implemented host integration fixture exporter writes manifests and CSD to `BLUE_MIXER_EVIDENCE_DIR` in capture mode. `BLUE_MIXER_BASELINE_DIR` identifies immutable baseline artifacts in compare mode. Both paths use native host forms and are developer-only; malformed manifests/missing fixtures fail explicit runs. No fixture is generated by mechanically rewriting candidate strings into a guessed baseline.

## Implemented supplied-CSD benchmark mode

Extend `benchmark_engine` with `--csd FILE`, mutually exclusive with the fixed `--scenario` selection, plus the existing `--trials`, `--warmup-cycles`, `--measure-cycles`, `--output`, and `--json` arguments. The new mode derives `sr`, `ksmps`, and output layout from the supplied CSD instead of hardcoding the fixed benchmark's 48 kHz/32 values. Existing invocations without `--csd` behave exactly as before.

Extend `native/blue-engine/scripts/benchmark.mjs` with `--csd CANDIDATE` and `--baseline-csd BASELINE` for the new mode. Validate combinations and pair metadata before running. The wrapper uses the same newly built Release executable and selected Csound runtime for baseline/candidate; it does not compare results from different engine builds. Preserve the old `--baseline` fixed-scenario JSON contract; reject ambiguous combinations rather than silently interpreting it as a CSD file.

The wrapper runs at least seven paired measured trials, interleaving baseline/candidate order with a recorded fixed seed. Each trial excludes compilation/startup, uses at least 1,024 warmup cycles and 65,536 measured cycles, and must complete the requested window. Fixture score duration must cover that window for its own rate/block setting. Early completion, partial window, zero/NaN metrics, mismatched metadata, unavailable runtime, and unsupported arguments fail the run.

No audio device, file-output writes, GUI, network updates, or concurrent validation jobs run in the core timing window. Use the same audio sources and control setup in both CSD files. Run float64 output comparisons separately; do not strip different DSP/routing from the two timing inputs. Compile/startup, allocation and whole-process CPU may be supplemental fields only with distinct measurement labels.

## Metrics and gates

Primary metric is `performKsmpsAvgUs` or its clearly named new-mode equivalent: mean steady-clock elapsed Csound performance time per audio block within a trial, summarized by median across trials. Report units and clock explicitly. It is not CPU time and must never be labelled as such. Keep host-cycle latency separately labelled; do not silently compare a host average with a Csound-only average.

- **Primary improvement**: at least 10% reduction in the fixed primary fixture's median metric at both ksmps 32 and 64 on the recorded reference machine.
- **Regression bound**: no repeatable increase above 5% for each representative fixture, eligible shape and tested block/platform. Confirm an apparent regression in an independent paired run before attributing it to a candidate; retain both result sets. Correctness must already pass, regardless of timing.
- **Candidate adoption**: positive/negative eligibility tests, double/live render proof and matched generated-workload results all pass. Record the eligible threshold/shape and supported environments. If evidence cannot establish a deterministic common selection rule, defer the candidate; do not add host-specific generator switches.
- **Completion**: record macOS, Windows and Linux correctness/performance evidence; ordinary PR matrix success or opt-in skips do not count. Missing native evidence remains incomplete and cannot be labelled accepted.

No thresholds are applied to three-run archived algebraic results, unrelated historical automation scenarios, or measurements with different runtime/compiler/settings. Compiler/runtime upgrades require fresh matched evidence for performance claims.

## Workload matrix

| Fixture                | Definition/purpose                                                                                                                                                                                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary send-heavy     | 128 stereo source strips, four enabled non-unity sends each to an eight-subchannel feed-forward graph, live gate generation, unity/non-unity level controls, panning off and metering off, no effect UDOs; complete generated mixer and cheap identical source instruments |
| Small                  | One and 16 strips, zero/one sends, including no-op/unity paths                                                                                                                                                                                                             |
| Fan-in                 | 64/128 strips with destination groups of 2/4/8/16/32; unweighted and weighted cases, existing direct destination contribution                                                                                                                                              |
| Barrier-rich           | Pre/post sends around original controlled nonlinear/stateful effects and nested global observers; must preserve or decline regrouping                                                                                                                                      |
| Panning/metering       | Mono/stereo layout, all supported modes, live controls, metering off/on                                                                                                                                                                                                    |
| Compatibility/control  | Disabled mixer, disk fixed/pruned routes, timeline and BlueLive, source sound then silence                                                                                                                                                                                 |
| Representative project | Original deterministic instrument/effect workload with realistic DSP cost, separately labelled from mixer-dominated fixtures                                                                                                                                               |

Reference performance blocks are 32/64/128 at 44.1/48 kHz; the primary SC-001 gate uses 44.1 kHz and 32/64. Correctness includes ksmps 1. Candidate fan-in crossover evaluation covers each listed group size before choosing a fixed threshold. Sparse/quiet cases do not justify deleting stateful processing.

## New-mode report shape

Use a new explicit `benchmarkKind: mixer-generated-csd` and `schemaVersion: 1`, separate from the unchanged historical fixed-scenario report. Retain:

- Fixture ID, source-input hash, generation profile, baseline and candidate Blue revisions/dirty-diff hashes, CSD hashes and binding-manifest identities.
- OS/version, architecture/CPU, compiler/version/flags, Release engine build revision/hash, Csound version/build or library hash and double-sample precision, exact runtime options/thread count, sample rate, ksmps, channel count.
- Clock/metric names/units, warmup/measured cycles, repetitions, interleaving seed/order, raw per-trial samples, median, spread, percentage delta, and gate verdicts.
- Scenario/candidate accept/defer/reject ledger with rationale and linked audio-equivalence results. Native argument/parser/report checks cover missing inputs and incompatible combinations.

Use `path.join`/native filesystem operations for artifact paths; only embedded Csound strings use the existing Csound path escaping boundary. Cover spaces and synthetic Windows paths, and obtain native Windows execution evidence. No new production filesystem path convention is introduced.
