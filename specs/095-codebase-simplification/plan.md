# Implementation Plan: Codebase Simplification & Overengineering Reduction

**Branch**: `095-codebase-simplification` | **Date**: 2026-09-02 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/095-codebase-simplification/spec.md`

## Summary

Execute a phased, incremental simplification across the monorepo based on ponytail-audit findings:
1. Prune dead Java Swing mirror artifacts, unused provider hierarchies, and static clipboards from `@blue/data`.
2. Modernize hand-rolled utilities to standard platform primitives (`crypto.randomUUID()`, `@floating-ui/dom` via `useHostSurface`, standard `Error.cause`).
3. Prune transient audio glitch diagnostic classes (Spec 093) and flatten over-engineered domain IPC registration sequencing in the Electron main process.
4. Retain `quickjs-emscripten` in `blue-cli` and `clsx`/`tailwind-merge` in `@blue/app`, deferring UI styling normalization to a follow-up specification.

## Technical Context

**Language/Version**: TypeScript 5.8+, Node.js >= 20, Electron 35 (Chromium 134)  
**Primary Dependencies**: React 19, `@floating-ui/dom`, `zustand`, `esbuild`, `vitest`  
**Storage**: Canonical `.blue` XML project files, in-memory `BlueData` document  
**Testing**: Vitest across all workspace packages (`@blue/data`, `@blue/app`, `blue-cli`, `@blue/engine-client`)  
**Target Platform**: macOS (Apple Silicon & Intel), Windows 10/11 x64, Linux x64  
**Project Type**: Monorepo with portable data library (`@blue/data`), Electron application (`@blue/app`), CLI (`blue-cli`), and engine protocol (`@blue/engine-client`)  
**Performance Goals**: Zero degradation in project load/save, CSD compilation, or editor window open speeds; reduced bundle and runtime memory footprint  
**Constraints**: Absolute preservation of `.blue` XML roundtrip fidelity and Java Blue CSD compilation parity; browser-safety of `@blue/data`  
**Scale/Scope**: Clean removal of ~1,400 lines of dead code and redundant algorithms across 3 phases in discrete, reviewable single-commit tasks

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **Portable data core**: **PASS** — `@blue/data` source remains platform-neutral, browser-safe, and free of Node.js built-ins, DOM-only APIs, Electron APIs, and dynamic imports. `crypto.randomUUID()` is universally supported on `globalThis.crypto` across Node 20+ and modern browser/Chromium environments.
- **Java and project compatibility**: **PASS** — `.blue` XML serialization, attributes, tags, and CSD generation remain bit-for-bit identical to Java Blue references. The removed classes (`LayerGroupProviderManager`, `LayerGroupListener`, `CopyBuffer`) were Java Swing client wiring and have zero impact on project persistence.
- **Canonical ownership and contracts**: **PASS** — Electron main process remains the sole owner of active `BlueData` documents. Flattening domain IPC registration simplifies registration mechanics while keeping all channel names, payload types, and error behaviors unchanged.
- **Runtime and engine isolation**: **PASS** — Engine protocol contracts in `@blue/engine-client` remain stable. Main process owns host process and native library lifecycles; renderer remains bound to typed IPC channels.
- **Host-path portability**: **PASS** — No changes to filesystem path handling or external text boundaries.
- **Verification evidence**: **PASS** — Verification proceeds commit-by-commit via targeted package tests (`pnpm --filter @blue/data test`, `pnpm --filter @blue/app test`), XML roundtrip fixtures, and full repository verification (`pnpm test`, `pnpm lint`, `git diff --check`).
