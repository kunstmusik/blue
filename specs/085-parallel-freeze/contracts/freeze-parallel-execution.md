# Contract: Parallel Freeze Execution

Main-internal contract for `executeFreezeUnfreeze` in
`packages/blue-app/src/main/freeze-score-objects.ts`. Extends the sequential behavior
specified by spec 056's render/freeze parity contract; observable freeze outcomes
(artifact naming, `FrozenSoundObject` construction, unfreeze cleanup, atomic commit)
are unchanged. Spec: [085-parallel-freeze](../spec.md).

## Inputs

```ts
interface FreezeContext {
  data: BlueData;                  // canonical project (mutations only in commit phase)
  projectDirectory: string;        // saved project directory (unchanged)
  utility: UtilitySettingsSnapshot; // now includes freezeMaxJobs (integer 1–32)
  platform: string;
  isCancelled?: () => boolean;
  javaScriptSession?: JavaScriptSession;   // used only in the sequential prepare phase
  javaRuntimeClient?: JavaRuntimeClientContract | null;
}
```

`freezeMaxJobs` is read once at operation start. Values ≤ 0 or non-integers are
treated as 1 (defense in depth; the settings layer already normalizes to 4).

## Execution phases

1. **Resolve** (unchanged) — target resolution, per-item `pending` events, rejection reporting.
2. **Prepare** (sequential, per freeze target) — `buildFreezeRenderData` →
   `generateDiskCsd` → `allocateFreezeFileName` → `writeTempCsdSnapshot` →
   `planFreezeCommand`. A prepare failure rejects that target only (per-object).
   Cancellation between preparations aborts with no artifacts to clean for
   unprepared targets.
3. **Render pool** (bounded concurrency `min(freezeMaxJobs, pendingJobs)`) — each job:
   seam `runCsound` → artifact existence/format/duration inspection →
   `FrozenSoundObject` construction → staged. Dispatch order is input order; completion
   order is arbitrary and never observable in results, filenames, or progress.
4. **Verify + commit** (unchanged) — all sources still in place, then atomic
   replacement, `complete` item events, reference-counted unfreeze cleanup.

Unfreeze targets are staged during phase 2 without preparation and never occupy
render-pool slots.

## Seam extension (main-internal)

```ts
interface FreezeExecutionSeam {
  runCsound(args, cwd, onProgress?, totalDuration?, onOutput?): Promise<{
    exitCode: number;
    stderr: string;
    stdout?: string;
    cancelled?: boolean;
    errorCode?: string | null;   // NEW: pass-through of EngineRuntimeService codes
  }>;
}
```

## Failure classification

| Class | Signals | Effect |
|-------|---------|--------|
| Systemic | seam `errorCode` ∈ {`CSOUND_UNAVAILABLE`, `ENGINE_CAPABILITY_MISSING`, `CSOUND_EXECUTION_INVALID_CWD`, `CSOUND_PROCESS_FAILED`} or unavailable runtime service; cancellation signal set | Stop dispatching jobs and abort all in-flight jobs immediately (via the operation's shared abort controller), then clean up |
| Per-object | nonzero render exit with no systemic code; artifact missing/format-mismatch/no-duration; prepare-phase failure (incl. CSD generation) for one target | Stop dispatching new jobs, let in-flight jobs finish, discard their staged artifacts, then clean up |

Shared-flag misconfiguration surfaces as per-object failures across every job; the
operation still fails all-or-nothing — only the early-stop optimization is skipped.
Both classes report rejected targets with reasons and make zero score mutations.

## Cancellation

- Before dispatching each job and after each job settles, the executor checks `isCancelled()`.
- The main-process cancel handler flips the signal and aborts the shared controller, which cancels every in-flight engine execution at once.
- Terminal state: `cancelled` result, no replacements committed, every artifact generated by the operation removed, temp CSD snapshots cleaned after the pool settles.

## Progress

- Rendering phase: `(completedJobs + Σ(inFlightJobProgress / 100)) / totalRenderJobs` scaled into 0–90.
- `committing` = 95, `completed` = 100; 100 only on success. Values never decrease as a function of job completion (per-job Csound progress is monotonic in aggregate).
- Message text reports counts (`N rendered, M running`); per-item rows continue on `FREEZE_ITEM_STATUS_CHANNEL` (`FreezeItemStatus`).

## Per-item events (focus and completion timing)

- Item phases: `pending` → `running` (dispatch) → `rendered` (render finished and staged) → `complete` (after the atomic commit) or `failed`. `complete` is only ever emitted post-commit.
- Renderer focus model: the progress dialog's output console follows one focused row, defaulting to the first object; only a user row click changes focus. Item events (running, output chunks, rendered) never move the selection — under parallel interleaving, following events would flash the highlight across every row.
- A `rendered` row that never commits (operation failed or cancelled downstream) settles to the renderer-derived `notApplied` state; `rendered` never implies the score changed.

## Invariants

- At most `freezeMaxJobs` seam `runCsound` calls are unresolved at any moment (FR-001).
- With `freezeMaxJobs = 1`, dispatch is strictly one-at-a-time in input order — equivalent to the prior sequential executor (FR-005).
- One operation ⇒ pairwise-distinct `freezeN` artifacts, allocated during sequential preparation; no file is ever overwritten (FR-006).
- No score mutation before every job has succeeded (FR-007); staging verification runs after the pool settles.
- `javaScriptSession` / `javaRuntimeClient` are never used concurrently (prepare is sequential) (FR-011).
- Temp CSD cleanup (`cleanupTempCsdSnapshots`) runs after the pool settles on every path (success, failure, cancel) (FR-012).
- The single-active-operation guard in the main handler is unchanged (FR-010).
