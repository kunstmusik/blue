# Data Model: Code Repository

## Persistence boundary

The Code Repository is an application-level user library. Its canonical durable state is the
main-owned `blue_code_repository.sqlite` database under Electron user data. It is not part of
`BlueData`, `.blue` XML, the project snapshot bridge, or the unified-library database.

The main process owns file paths, database access, migration, recovery, and revision updates.
`@blue/data` owns only serializable model values and the legacy XML codec. Renderer tree drafts,
editor selections, and generated context-menu items are transient.

## Repository tree

### `CodeRepositoryDocument`

Represents the complete user-visible repository.

| Field | Type | Rules |
|---|---|---|
| `root` | `CodeRepositoryGroup` | Exactly one root; root ID is stable and protected |
| `contentRevision` | non-negative integer | Starts at `0` and increases after every committed mutation |
| provenance | internal database metadata | Describes migration/import origin and is never exposed as XML node data |

The serialized renderer snapshot contains the root tree and revision. Internal database metadata
is not sent to the editor menu unless needed for conflict handling.

### `CodeRepositoryNode`

Every node has:

| Field | Type | Rules |
|---|---|---|
| `id` | UUID string | Stable across edits and database reload; regenerated by legacy XML import because XML does not serialize IDs |
| `kind` | `root \| group \| snippet` | Determines allowed fields and operations |
| `name` | string | Required, user-editable, may duplicate sibling names |
| `parentId` | UUID or null | Root is null; all other nodes have an ancestor group |
| `order` | non-negative integer | Unique ordering position among siblings after normalization |
| `children` | ordered node list | Present for root/group; absent or empty for snippet |

Additional snippet fields:

| Field | Type | Rules |
|---|---|---|
| `code` | string | Required for snippets; empty string is valid; preserve exact text |

Groups cannot have code. Snippets cannot have children. The root cannot be renamed, moved, or
deleted. A move cannot place a node under itself or one of its descendants.

## SQLite representation

The dedicated database contains normalized rows rather than one opaque XML document:

```text
code_repository_nodes(
  id TEXT PRIMARY KEY,
  parent_id TEXT REFERENCES code_repository_nodes(id),
  kind TEXT NOT NULL CHECK(kind IN ('root', 'group', 'snippet')),
  display_name TEXT NOT NULL,
  code_text TEXT,
  sort_order INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
)

code_repository_state(
  singleton_id INTEGER PRIMARY KEY CHECK(singleton_id = 1),
  content_revision INTEGER NOT NULL,
  initialized INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
)

code_repository_imports(
  id TEXT PRIMARY KEY,
  source_path TEXT NOT NULL,
  source_hash TEXT NOT NULL,
  source_kind TEXT NOT NULL,
  status TEXT NOT NULL,
  node_count INTEGER,
  diagnostics TEXT,
  imported_at INTEGER NOT NULL
)
```

The repository layer must enforce root, parent, kind, code/nullability, cycle, and order
invariants in addition to SQLite constraints. All multi-row changes occur in one transaction.

## XML mapping

| XML element | Model |
|---|---|
| `customAccelerators` | Protected repository root |
| `customGroup name="..."` | Group node with ordered child elements |
| `customAccelerator` | Snippet node |
| `name` | Snippet display name |
| `signature` | Exact snippet code text |

Export uses canonical XML formatting and omits UUIDs, revisions, and database provenance. It must
escape names correctly and preserve snippet code content. It need not preserve the original source
file's formatting or attribute quote style.

## Migration state

`blue-code-repository-state.json` is separate from the repository database so a failed or
partially completed database upgrade can be diagnosed without relying solely on the database that
may be unavailable. It records:

- schema version and initialization status;
- attempted source path and content hash;
- migration status: `not-started`, `succeeded`, `failed`, or `skipped`;
- diagnostic code/message and timestamp;
- whether a historical packaged-default seed was recorded by an earlier build (retained only for
  migration-state compatibility).

The database also records successful import provenance and source node counts. A matching
successful source hash is never automatically imported again.

## State transitions

```text
not initialized
  ├─ valid legacy XML ───────────────> imported / ready
  ├─ no legacy XML ──────────────────> empty root / ready
  └─ invalid or unreadable XML ──────> failed / recoverable

ready
  ├─ atomic edit commit ─────────────> ready with revision + 1
  ├─ stale expected revision ────────> conflict; current data unchanged
  ├─ explicit import ─────────────────> imported / ready with revision + 1
  └─ explicit export ─────────────────> ready; database unchanged
```

## Validation rules

- Exactly one root row exists and has no parent.
- Every non-root node has exactly one reachable group/root ancestor.
- No node can be its own ancestor.
- Root and group code fields are null; snippet code is non-null, including empty string.
- Sibling order is deterministic and normalized after move/reorder operations.
- Names are non-empty after the UI's normal name validation; duplicate names are allowed.
- XML import is all-or-nothing. Unsupported or malformed input produces diagnostics and does not
  modify the current repository.
- Legacy sources remain untouched by migration and import.
